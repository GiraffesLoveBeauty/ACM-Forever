# 题库读取优化、索引迁移与性能验证（#155）

> 状态：已实现，等待 PR 评审与生产迁移验收。基线为 main 的 `91a3ad6`。本文记录实现与验证，不代表已经部署。

## 范围与复用

优化公共题库首屏/切换平台/分页、标签选项、原始及洛谷原生标签组合筛选、本人 AC 查询。详情、收藏、题单、训练任务、比赛进度和统计继续使用既有接口与权威数据。

| 已有能力 | 本次复用或改造 | 必要新增的理由 |
| --- | --- | --- |
| `problem_bank.py`、`problem_sync.py`、各 OJ 同步与任务流程 | 保留现有采集、事务、任务取消和失败回滚；服务数据库连接统一使用 `ListingConnection` | 在提交同一事务时更新派生查询索引，避免重复实现同步器 |
| `problem_listing.py` | 将原有列表时间整理扩展为轻量查询摘要、统一条件与分页 | 请求阶段全站 UNION/窗口去重是瓶颈，需要可索引的读取结构 |
| `problem_tracker.py` | 继续使用 `problem_id_key/problem_id_aliases` | 只在变更写入/迁移中归一化，不再每次列表读取计算全库题号 |
| `problem_tags.py`、`luogu_problem.py` | 复用标签解析与原生分类参数校验、当页分类补充 | 同步维护标签关系及有效选项，筛选不再逐题解析文本或 JSON |
| `problem_time.py`、既有难度元数据工具 | 保留时间/数值难度契约，增加原站时间未知筛选 | 持久排序键，避免请求时全库聚合时间 |
| `MemberProblems.vue`、`lib/api.js` | 保留请求取消、独立标签加载与晚到响应保护 | 增加页面实例内的标签版本缓存及下一页游标 |

删除后台 API 中不再调用的 `_PROBLEM_QUERY`、`_MEMBER_PROBLEM_QUERY` 及其专用 UDF 注册器。基准脚本中保留一份冻结的旧查询，只用于同数据对照，不参与服务运行。未增加依赖、并行题库、独立同步器或另一个标签体系。

## 数据结构与更新一致性

`crawler_problems`、`recommendations`、`submissions`、`user_problem_state` 仍是权威来源；以下表均为可重建的查询结构，不是另一套题库。

| 派生表 | 保存内容及主要索引 |
| --- | --- |
| `problem_listing` | 每个 OJ/标准题号一条轻量摘要：题名、链接、原始标签、数值/原生难度、时间和排序键；主键 `(platform,id_key)`，全局与平台时间顺序索引、难度/时间范围索引。无题面、样例或 PDF |
| `problem_listing_tags` / `problem_listing_tag_options` | 题目—原始标签关系和按平台维护的有效标签/引用计数；完整标签忽略大小写，删除最后引用时清理选项 |
| `problem_listing_native_tags` | 洛谷题目—原生标签 ID 关系及展示顺序，保留洛谷原生等级和多标签交集 |
| `member_problem_index` | 共享关联表，主键 `(owner,platform,id_key)`；必要 AC 时间及排序键、收藏/状态、本人标签回退。成员/OJ/AC 顺序索引使个人记录连续可读，不为每个成员建物理表，不复制题名/难度/题面 |
| `member_problem_tags` | 本人标签回退关系，仅在公共有效标签为空时参与该成员的查询和选项；不进入公共词表 |
| `problem_listing_dirty` / `member_problem_dirty` | SQL 触发器写入的去重变更队列；保留可恢复的变更题号/成员范围 |

服务使用 Python sqlite3 支持的 connection factory，通过既有 aiosqlite 连接接入。在 `commit` 内先刷新本事务涉及的题目/成员索引，再提交源记录；任何一步失败则源数据与索引一起回滚。题面正文、PDF、样例或采集状态的单独更新不会触发目录重建。比赛时间改变时只将该场目录题目入队。重复同步内容不变时不重写公共摘要、个人关联/标签关系或缓存版本。

公共标签来自采集目录、推荐目录的第一份非空标签；缺少公共标签时仅允许本人的 AC 标签回退。其他成员的私人标签和状态不进入本人的返回结果。解绑/换绑复用现有证据清理；注销复用现有私人数据删除。触发器及同事务提交随之删除派生关联，最后一条个人关系消失时删除其缓存版本键；重新写入时使用新的不透明版本，避免缓存误命中。既有账号代次/绑定版本校验继续阻止过期同步回写。

## 读取与复杂度

- 公共目录：条件筛选与精确 COUNT 共用同一个构造器，按排序索引分页；只对当前页批量补当前成员的收藏/必要标签。列表 SQL 不读 submissions、recommendations、crawler_problems 或题面大字段。
- 本人 AC：从 `(owner,platform,ac_order,id_key)` 范围读，再由 `(platform,id_key)` 关联轻量目录；正常页面无全量个人临时排序，更不聚合其他成员 AC。
- 原始标签：通过标签关系找到候选，不按题逐行解析字符串。洛谷多标签通过关系表的主键 EXISTS，数值/原生难度与时间在分页前过滤。
- 标签选项：公共平台词表加本人必要回退，不依赖全站 AC；网页按平台复用，切换平台时使用 60 秒有效期，并依据列表/标签响应的 tags_version 刷新；晚到的旧版本标签会在请求结束后重取。
- 分页：连续翻页优先使用 next_cursor；旧客户端、跳页、刷新直链仍兼容 OFFSET。游标绑定成员、筛选、页大小及下一页页码，改条件即丢弃。

仅讨论无额外筛选的个人页数据定位，设全站 AC 关系 A、题库 N、每页 K，成本约 `O(log A + K + K log N)`；公共目录按索引取页约 `O(log N + K)`，再做 K 条私人状态关联。返回的精确 COUNT 仍可能处理本人 U 条或所选平台 N 条，标签组合可能读候选集合并排序；模糊搜索仍使用 LIKE、可能扫描所选范围。OFFSET 深页也有跳过记录的成本。没有将所有端到端请求宣称为只与 K 有关。

游标不是数据库快照：新题按稳定排序键插入时能继续原锚点，改变时间或删除大量记录后应重载第一页。详情与分类补充沿用既有工具；洛谷列表的分类补充使用该工具的 indexed 模式，只读取当页原生难度/标签 ID 与字典，不读包含 Markdown 正文的 metadata_json。详情继续读取原元数据。原生标签索引缺少展示顺序列时自动补列并刷新洛谷索引，保留来源标签顺序。AtCoder 难度补充只处理当页。

## 时间规则

已知原站可核验时间的题目在前，降序排列；当前 CF/AtCoder 使用已保存比赛开始时间，返回依据 `contest`，不声称是精确创作时间。洛谷不伪造原站发布时间。未知时间题目在后，按不可变的首次收录时间倒序，再按平台/标准题号稳定排序。迁移优先读取 crawler_problems.created_at；没有历史收录时间的来源从首次建立摘要起计。补到可靠时间后按来源时间归位，刷新题面或标签不置顶。

`time_basis=unknown` 独立选择原站时间未知题目，不接受 start_at/end_at；网页清空并禁用日期框。明确的比赛发布时间范围不会混入未知题目。本人 AC 仍按 AC 时间倒序，洛谷 ac_at=0 继续表示已 AC 但时间未知，不能因真假判断漏掉。

## 迁移、部署与恢复

1. main 合并会触发生产部署，合并前由维护者备份现有 SQLite，确认数据库路径、可用空间和维护窗口。备份复用既有 SQLite 备份方式；运行中不要只复制主 .db 而遗漏 WAL。
2. 沿用服务启动时的 connect_db 或现有初始化命令。首次自动创建派生结构、源表身份索引、变更触发器并回填；完成后在 settings 中保存 problem_listing_version。原始题号、AC 时间、收藏和训练引用不改写。
3. 相同版本重复初始化不会全量回填；未提交失败整体回滚，下次启动继续初始化。已存在的持久变更队列会在启动提交时补齐。回填需要时间和额外磁盘空间，生产数据量不同，应预先在数据库副本测量。
4. 服务内所有题库/AC 写入口均接入同一 factory。外部脚本若要写后立即可见，应复用 connect_db 或 ListingConnection。旧的原生 SQLite 写入仍能成功并留下持久队列，但必须在恢复服务前运行初始化/重启来补齐；没有后台轮询来自动吸收运行中外部脚本。
5. 发现问题时保留备份与失败日志，停止并发写入；可回到 PR 前代码读取原权威表。旧代码的 SQL 写入不依赖 Python 自定义触发器函数，因此不会因缺少 UDF 被阻断。回到本版本后初始化会补齐积累的队列。若要恢复完整备份，按既有运维恢复流程同时处理 WAL。
6. 如派生表遭破坏，需要维护者在备份副本验证后清理本模块的 listing_* 触发器、八张派生表与 problem_listing_* 版本键，再沿用初始化回填。不要删除四张权威源表、修改原始题号或直接在运行中的生产库手工修表。

## 性能与验证

基准脚本：`python feat/api/tests/benchmark_problem_listing.py --problems 20000 --ac 100000 --repeats 3`。只创建临时合成数据库，不读取生产配置/数据；比较冻结旧 SQL 与新读取工具，并核对每个场景的总数和返回题号一致。合成目录全部为 Codeforces，每页 20，本人 1000 条 AC；所有题目有来源时间，避免旧/新时间语义差异混入性能对照。

测量版本为本 PR 的 ca09bae（后续改动补充洛谷分类摘要读取，未改 CF 基准读取路径）。2026-11-17，本机 Windows-11-10.0.26200-SP0，Python 3.12.14，SQLite 3.53.1。fresh_connection 指新建 SQLite 连接，仍保留操作系统文件缓存；warm 为同连接重复三次中位数。SQL 耗时不包含 HTTP、会话鉴权、网络、详情分类补充或浏览器渲染，不能当作线上加载时间。

| 场景 | 旧 fresh（ms） | 新 fresh（ms） | 旧 warm 中位数（ms） | 新 warm 中位数（ms） | SQL 次数（旧→新） |
| --- | ---: | ---: | ---: | ---: | --- |
| 题库首屏 | 8281.939 | 19.783 | 8296.622 | 6.115 | 2→4 |
| 标签选项 | 4254.41 | 7.488 | 4256.462 | 1.089 | 1→1 |
| 单标签筛选（math） | 8963.708 | 69.095 | 9324.138 | 69.334 | 2→4 |
| 本人 AC | 7552.031 | 22.635 | 7723.2 | 12.388 | 2→4 |
| 第 501 页（OFFSET 兼容） | 8023.048 | 15.546 | 8650.415 | 6.745 | 2→4 |

新列表的四条 SQL 分别是精确 COUNT、当前页、当页私人状态批量关联、缓存版本；标签本身只需一条查询，HTTP 标签响应另读版本键。查询次数略有增加，但每条职责和读取范围更小，避免用次数下降冒充实际速度提升。默认首屏与本人 AC 的页数据不使用临时排序；标签筛选会对候选排序。旧路径反复执行全站 UNION、窗口函数与时间聚合，并存在临时 B-tree。

计划核对：公共目录与其 COUNT 使用 idx_listing_platform_newest；本人页和 COUNT 都首先使用 idx_member_platform_ac_page(owner,platform)，再按目录主键定位；单标签先使用 idx_listing_tag_lookup/idx_member_tag_lookup 定位候选，再读目录。原始标签、原生标签的任意组合仍有候选集合和精确总数成本。

固定 N=20000、本人 U=1000，仅将其他成员 AC 从 100000 条总关系扩展到 200000：公共列表 11.616→7.869 ms、标签 1.105→0.61 ms、本人 AC 13.689→10.08 ms。这里是单次扩容对照，会有缓存和系统负载波动；结论是查询计划没有增加全站 AC 扫描，不能解释成“其他人数据越多越快”。

首次旧库建表/索引及回填 20.804 秒，SQLite 逻辑页增长约 55.3 MiB；包括新摘要、关系及源表身份索引，不是纯 AC 关系体积，也不是 WAL 峰值或压缩后文件大小。增加 100000 条其他成员 AC 的源写入加同步索引共 40.48 秒。读取收益以额外存储与同步写入成本换取，生产环境应在副本中核对维护窗口。
