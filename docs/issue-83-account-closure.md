## 1. 一句话结论

采用“**账号生命周期墓碑 + 原子撤销登录与私有数据清理 + 公共内容去标识化展示 + 所有写入入口统一拦截**”方案。复用现有 SQLite、凭据版本和 OJ 绑定版本，不新建认证体系，不把停用或退出登录冒充注销。

建议首期不提供撤销期、恢复、管理员代注销或同 QQ 重新开户；管理员先交接并降为普通成员。以上是**推荐策略，不是团队已确认结论**，须按第 3 节确认后实施。

## 4. 范围和其他任务的边界

### 4.1 本任务负责

- 个人中心入口、影响预览、重新认证、明确确认、提交及结果页。
- 后端生命周期状态、会话与密码撤销、关联数据处理、操作回执和审计。
- 注销与其他写入并发的安全边界；阻止同步、Bot、导入和启动引导恢复账号。
- 已注销公共作者展示、头像/主页/接口去标识化以及旧文件 URL 访问控制。
- 迁移、自动化测试、多端联调、发布和故障恢复约束。

### 4.2 不在首期顺带建设

- 不新增管理员代注销，不提供恢复/宽限期/同 QQ 重开。
- 不删除或修改外部 OJ 账号，不承诺远端缓存、他人截图或公共正文中的个人信息自动消失。
- 不重写认证，不引入 Redis、消息队列或新的数据库。
- 不做 #84 的 Excel 导入页面和业务；但提供其必须调用的生命周期守卫与冲突规则。
- 不做 #85 的管理中心重构；仅返回其所需的注销状态与受限操作原因。
- 不代替 PR #48 的 Android 功能开发；只明确服务端约束及发布前联调门槛。

## 5. 方案取舍

| 方案 | 问题/成本 | 结论 |
| --- | --- | --- |
| 直接物理删除 `users` | 公共内容外键/作者引用受损；机器人可以再次建档；无法阻止同 QQ 继承旧数据 | 不选 |
| 仅 `is_active=0` 或清 Cookie | 等于停用/退出登录；旧自动写入、资料和启用入口未被治理 | 不选 |
| 迁移整站到全新 user UUID 并支持重开户 | 长期有价值，但需要迁移所有 owner/author 与客户端契约，明显扩大 #83 首期范围 | 留给允许重开户的后续设计 |
| 生命周期墓碑 + 共用守卫 + 事务清理 | 兼容当前 QQ 主键，保留公共引用；需诚实披露最小标识仍保留 | 推荐 |

这里的“去标识化展示”不是不可逆匿名化：受限数据库仍能关联原 QQ 与保留内容。若项目要求连最小 QQ 都不能保留，应改用新的主体标识和受控映射方案，不能沿用本设计却宣称已彻底匿名。

## 6. 状态和权限规则

### 6.1 两个维度分开

- 成员身份：现有 `users.status`，继续表示原业务身份；不写入“已注销”来代替状态机。
- 生命周期：新增 `users.account_state`，只取 `active / closed`。
- 登录启停：现有 `web_accounts.is_active`；`active + is_active=0` 仍只是临时停用。

```text
未开户成员：users.active，无 web_accounts
已开户可用：users.active + web_accounts.is_active=1
暂时停用：users.active + web_accounts.is_active=0
已注销：users.closed + web_accounts.is_active=0 + 凭据已撤销
```

首期只允许 `active -> closed`，不允许 `closed -> active`。无 Web 账号的成员不能只凭 QQ 发起注销；缺少本人认证方式时走另行批准的人工身份核验流程，本任务不创造免认证入口。

### 6.2 管理角色保护

- `member`：通过当前密码验证和确认后，可注销本人。
- `admin / root`：注销预览返回 `ROLE_HANDOVER_REQUIRED`；交接并由另一 root 降为 member 后重新登录、重新预览。
- legacy root：没有成员 QQ，不能调用本人注销接口，也不计入可交接的真实 root 数量。
- 同一个公共函数校验启停、降级、删除等所有角色变化，不只保护新的注销接口。
- “可用 root”须同时满足：生命周期 active、登录启用、凭据有效，且不因当前临时密码过期而被登录逻辑拒绝；定义应与登录判断一致。
- 在一个 `BEGIN IMMEDIATE` 写事务内重新校验操作者权限、目标状态及 root 数量；不使用请求开始时缓存的角色，不用进程内锁作为最终保证。
- 两名 root 并发互相降级/停用时，最多一个相关操作成功，不能留下零个可用 root。

## 7. 数据模型：最小必要增量

以下均为拟新增，不代表基线已存在。由迁移负责初始化，所有查询使用显式列名，避免 `SELECT *` 把新增内部信息带到客户端。

### 7.1 `users` 增加生命周期字段

| 字段 | 建议定义 | 用途 |
| --- | --- | --- |
| `account_state` | TEXT NOT NULL DEFAULT 'active'，取 active/closed | 跨 Web、Bot、同步与导入的唯一生命周期权威 |
| `account_epoch` | INTEGER NOT NULL DEFAULT 1 | 注销时单调递增，标识旧写任务失效 |
| `closed_at` | INTEGER NULL | 注销提交时间，Unix 秒 |

不额外维护一套相互独立的 Web 注销状态。`web_accounts` 继续保留一行：`is_active=0`、`credential_version += 1`、密码字段改为现有验证器必定拒绝的不可用标记、临时密码有效期清空、角色归为 member。每个登录/改密/管理入口必须再 JOIN `users.account_state`，不能只依赖不可用密码标记。

`password_hash` 现为 NOT NULL，不直接改成 NULL。保留已撤销账号行还能阻止启动引导因账号计数为零而误建 root。

### 7.2 `account_closure_requests`：原子结果和幂等回执

建议字段：

- `request_id`（随机 UUID 主键）、`user_qq_id`（受限关联）、`idempotency_key_hash`。
- `intent_fingerprint`（只包含动作、主体、策略版本、epoch 等非密码语义字段）。
- `policy_version`、`account_epoch_before`、`credential_version_before`、`committed_at`。
- `receipt_token_hash`、`receipt_expires_at`、`cleanup_state`（pending/complete/failed）。
- 唯一约束：`(user_qq_id, idempotency_key_hash)`；回执读取还必须验证秘密令牌。

不保存密码、密码摘要指纹、原 Cookie、原 CSRF 或明文回执令牌。此行与注销事务一起提交；无已提交行不代表客户端可以宣称注销成功。

建议回执有效期 24 小时，过期销毁令牌摘要，仅按已确认审计策略保留必要操作记录。该期限是待评审技术默认值。

### 7.3 `account_lifecycle_audit`：成功与失败审计

字段最小化：随机事件 ID、操作 ID、受限 actor/target、动作、结果码、策略版本、时间、必要的计数摘要。权限建议只给 root/指定运维审计人员；普通管理员不自动获得完整审计或原始资料。

成功记录与注销事务同提交；失败事件在原事务回滚后另行记录，不把失败记录回滚掉。审计写入失败不能报告注销成功；数据库本身不可用时仅输出脱敏故障码并告警，不把秘密请求体降级写进文件日志。记录失败码，不记录密码、令牌、原始请求体、完整画像或上游页面内容。

### 7.4 `account_closure_cleanup_tasks`：资源清理发件箱

字段：任务 ID、request_id、资源类型、受控存储标识、状态、重试次数、下次重试时间、租约时间、错误码。用唯一键防止重复建相同资源清理任务。

由现有服务生命周期启动轻量清理任务，不引入独立队列服务；重启后继续扫描。文件不存在视为已完成；无权限等真实错误按退避重试，失败可查询且不得“恢复账号补偿”。

### 7.5 敏感动作限频

建议新增 `account_sensitive_action_limits`，按账号和可信 IP 的受控键记录动作窗口与次数，使用短事务原子计数，跨进程有效。IP 键可用服务端密钥 HMAC，避免额外保存不必要的明文 IP。

可评审默认值：密码失败每账号 15 分钟 5 次、每 IP 15 分钟 20 次；预览和回执查询也需独立限频。复用现有可信代理 IP 解析，不直接相信客户端任意 `X-Forwarded-For`。

## 8. 数据处理清单与用户告知

以下是待 P03/P07/P08 确认后的推荐处理。实现必须由同一份处理规则生成预览摘要与执行计划，禁止“页面说删除，后端只隐藏”。

| 数据 | 建议动作 | 关键约束 |
| --- | --- | --- |
| QQ | 保留在最小墓碑与必要受限引用中 | 不向公开/普通本人接口返回；管理视图按需脱敏；明确不是 QQ 已从数据库消失 |
| `users.name/real_name/school/avatar_url/status` | 昵称改为“已注销用户”，其余清空；原身份字段不再参与展示 | 不以 QQ 回退昵称，不保留个人主页，不把原 `status` 当注销状态 |
| `last_sync_timestamp/challenge_rating` | 清零或回到无身份含义的默认值 | 排行榜和候选查询直接排除 closed 用户 |
| `web_accounts` | 停用、撤销密码和临时密码、增加凭据版本 | 启用、改密、重置密码、批量发密码一律不能恢复 closed |
| 五类 OJ 字段及 `account_bind_verifications` | 全部解绑，删除待验证信息 | 不操作外部 OJ 账号；所有绑定版本至少增加一次 |
| `user_platform_sync_state` | 删除该成员状态 | 老任务的成功/失败/游标回写必须先检查生命周期和版本 |
| `cf_practice_job_members` | 取消该成员分项，清除 handle/binding_key 等不再必要信息 | 不取消同批其他人；后台 `_member_update` 不能把已取消分项改回成功 |
| `cf_practice_jobs.payload/result/error_message` | 解析并去除或替换其中的个人标识 | 不是只删分项表就算完成；保留必要的全局任务统计，不破坏他人任务 |
| `submissions`、`submission_attempts` | 删除本人记录、提交尝试与保存的源码 | 不删除公共题库、题目元数据或其他成员记录 |
| `user_problem_state`、`review_states`、`contest_problem_reviews` | 删除收藏、题目状态、笔记与复习信息 | 事务内按本人 owner 字段匹配 |
| `study_plan_items`、`workspace_items`、`review_drafts`、`random_challenges` | 删除本人计划、工作台、复盘草稿和挑战 | 运行中的生成任务返回后不能重新插入 |
| `notification_preferences` | 删除订阅 | 提醒候选、发送前、发送结果回写都要检查 closed；已发出的外部消息无法撤回 |
| `forum_notifications` | 删除本人收件；本人作为 actor 的其他人通知解除关联/匿名展示 | 禁止新的通知写给 closed；不删除其他人的正常通知 |
| `forum_bookmarks`、`forum_post_likes` | 删除本人的收藏与点赞关系 | 公共计数随查询自然更新或主动失效缓存 |
| `forum_drafts`、本人待审/驳回帖子 | 删除草稿；按确认策略移除未发布内容并清正文/附件引用 | 避免待审核内容在注销后被管理员继续发布 |
| 已发布 `forum_posts/forum_comments` | 保留结构与正文，作者统一去标识化展示 | 保留回复树；不删除他人回复；关闭已注销作者的本人编辑能力 |
| Wiki 修订和分类操作历史 | 保留公共修订和最小必要审计引用 | 不直接修改受不可变约束保护的 author；管理/导出接口也不能默认返回完整原身份 |
| `wiki_requests/wiki_delete_previews` | 清除该主体的短期幂等/预览记录 | 不让历史写入请求在注销后复用权限 |
| `forum_reports`、`binding_audit`、审核人字段 | 按审计策略保留必要证据，隐藏不必要资料 | 不直接全部删除滥用处置证据；读权限、保留期和导出范围要确认 |
| 本人头像文件 | 立即撤销旧 URL 的访问，事务后异步物理删除 | 旧链接和条件请求不能继续命中本人头像 |
| `forum_images/forum_image_links` | 保留已发布内容仍引用的图片；清理未引用/仅私有引用图片 | 保留公共引用关系，去除多余 owner；不能按“本人上传”整批删而导致公共文章断图 |
| `markdown_assets/markdown_asset_references` | 按公开、草稿、历史修订的真实引用决定保留或清理 | `owner` 现为文本字段，需设计允许的关闭主体占位标识并同步授权代码，不盲目写 NULL |
| `settings` 等自由 JSON/文本 | 排查是否存了 QQ、通知对象、任务快照或原始资料 | 仅移除明确的本人关联，不误改全站管理员配置；确认职责已交接 |
| 日志、错误追踪、备份 | 新日志不再产生敏感明文；旧备份按已确认期限轮换 | 前台明确备份可能仍暂存；不承诺即时销毁所有离线副本 |

### 8.1 推荐告知文案

“注销后，你将无法登录本平台，现有会话失效；平台内 OJ 绑定、做题记录、收藏和其他私有资料将按清单清理。已发布的帖子、评论和 Wiki 内容按规则保留，作者显示为‘已注销用户’。平台会保留防止账号重建、维持公共内容引用及必要审计的最小记录。注销不影响外部 OJ 账号；备份按公示期限处理。首期不支持恢复或同 QQ 重新开户。”

文件尚在清理时单独显示“账号已注销，剩余文件清理中”，完成后再显示清理完成。不要使用“所有个人数据已全部删除”之类超出实际处理的文案。

### 8.2 公开内容隐私边界

- 统一作者投影：`author_name='已注销用户'`、`author_avatar_url=null`、`author_closed=true`，不额外返回 QQ、学校、OJ、个人主页或可还原头像地址。
- 尽量保留原 API 字段形状，增加明确状态；前端头像走现有默认头像，不生成 QQ 头像 URL。
- 已注销成员不出现在社区/管理统计候选以外的公开排行榜、搜索联想、成员详情或 OJ 绑定占用展示中。
- Wiki 公共序列化原本就会移除 `author`；保持该约束，补充已注销展示，并审查其他历史、管理和导出接口，避免为实现注销反而泄漏 author。
- 正文、图片或用户手写备注中的个人信息不会自动可靠识别。确认页说明公共内容保留规则，并提供已有内容申诉/人工处理渠道；不声称已全面扫描清除。

## 9. 接口契约（拟议）

遵循现有 API JSON 风格：`success/message/code`，错误码供多端使用。敏感响应统一 `Cache-Control: no-store`；密码、回执令牌不进入 URL、日志或分析事件。

### 9.1 `GET /api/me/account-closure-preview`

- 正常成员会话，目标只取服务端身份；不接受 QQ 作为注销目标。
- 首次登录未改密账号先返回现有 428，改密后才能进入注销；不把初始六位临时密码当长期认证凭据。
- 只读影响信息，不执行清理、不占业务写事务。生成随机操作 ID 和 256-bit 回执秘密供此次操作使用，不在数据库写入已提交结果。
- 返回影响数量、保留项、阻断项、当前策略和版本；统计只作当前快照，提交时重新计算真实处理范围。

```json
{
  "success": true,
  "policy_version": "closure-v1",
  "request_id": "<random-uuid>",
  "receipt_token": "<random-secret-not-for-logs>",
  "account_epoch": 1,
  "can_close": true,
  "blockers": [],
  "delete_counts": {"submissions": 120, "private_items": 8},
  "retain_counts": {"published_posts": 2, "wiki_revisions": 1},
  "retention_notice": "<负责人确认后的完整处理说明>"
}
```

回执秘密此时不授权任何动作；首次提交仍必须具有当前登录、正确密码与 CSRF。示例数字仅为测试数据，不是实际成员信息。

### 9.2 `POST /api/me/account-closure`

请求头：现有 `X-CSRF-Token`；`Idempotency-Key` 使用预览的随机 request_id；`X-Closure-Receipt` 使用回执秘密。

```json
{
  "current_password": "<仅在当前请求内使用>",
  "confirm_text": "注销账号",
  "policy_version": "closure-v1",
  "expected_account_epoch": 1
}
```

- 拒绝 `qq_id/owner_qq_id/target_qq_id` 等目标字段，不允许静默选另一个账号。
- 检查密码长度上限、固定确认文字、策略版本、类型和未知高风险字段；不对密码去空格或改大小写。
- 新执行要求完整认证、CSRF、限频和当前密码验证。管理员角色必须先完成交接。
- 操作意图只对非密码语义字段生成服务端指纹；不得持久化密码或可供离线猜测的密码指纹。
- 仅当事务提交成功，返回 `200` 与 `account_state='closed'`、`cleanup_state`、`request_id`，清当前 Cookie；服务端依状态/版本拒绝其他旧会话。

### 9.3 注销后重试与最小回执

不能简单给提交接口套 `member_required` 就结束：注销后旧会话会失效，网络超时重试可能先遇到 401，无法确认此前是否已提交。

推荐做一个**只读回放分支**：

1. 按操作 ID 找已提交结果，再以常量时间比较回执秘密摘要。
2. 匹配则只返回该次 `closed/cleanup_state`，不重新认证、不再次执行，不恢复通用身份，也不返回 QQ、计数或其他资料。
3. 无匹配结果时必须回到正常登录、CSRF、密码验证流程，不能用回执秘密发起新注销。
4. 同键但语义不一致返回 `409 IDEMPOTENCY_CONFLICT`；错误秘密使用统一失败响应并限频，不泄露操作是否存在。
5. 不同操作 ID 并发注销同一账号时，后到事务返回明确 `ACCOUNT_ALREADY_CLOSED` 或认证失效，不能重复清理/重复记成功事件。

另增只读 `GET /api/account-closures/<request_id>`，以 `X-Closure-Receipt` 查询最小回执，不接受 QQ。它无需旧登录，只能读取该条结果，24 小时后失效。未知/过期返回统一 404；网络失败显示“结果待确认”，绝不能自行显示成功。

前端仅在本次流程内存或短期 `sessionStorage` 保存操作 ID/回执秘密，以便刷新后确认结果；不写长期 `localStorage`，不保存密码。收到确定结果或过期后立即清除。

### 9.4 错误码建议

| HTTP | code | 客户端行为 |
| --- | --- | --- |
| 400 | INVALID_CONFIRMATION / INVALID_REQUEST | 保留页面，提示修改；不重试清理 |
| 401 | REAUTH_FAILED / AUTH_REQUIRED | 密码错误不泄漏哈希或账号细节；旧身份失效则确认回执后转登录 |
| 403 | CSRF_INVALID / LEGACY_IDENTITY_UNSUPPORTED | 不执行业务写入 |
| 409 | ROLE_HANDOVER_REQUIRED / LAST_ROOT_PROTECTED | 给出交接说明；后端再次验证，不能靠按钮禁用 |
| 409 | POLICY_CHANGED / ACCOUNT_CHANGED / IDEMPOTENCY_CONFLICT | 重新预览；不复用旧确认 |
| 409 或 410 | ACCOUNT_CLOSED / ACCOUNT_REOPEN_UNSUPPORTED | 已认证管理/Bot/导入操作明确拒绝恢复，不作为公开账号枚举能力 |
| 428 | MUST_CHANGE_PASSWORD | 复用首次改密流程 |
| 429 | RATE_LIMITED | 返回重试间隔，不继续密码计算 |
| 503 | STORAGE_BUSY / STORAGE_UNAVAILABLE | 不报告成功，保留操作回执信息供确认后重试 |

## 10. 核心事务：先验证，再一次性生效

建议新增 `account_lifecycle_service.py` 管理查询、守卫和角色约束，新增 `account_closure_service.py` 编排预览与关闭，路由只负责输入/输出。

### 10.1 锁外阶段

1. 解析并限制请求体；检查幂等结果回放分支。
2. 取当前本人身份、CSRF 和可信 IP，限频预留必须原子化。
3. 读取当前密码哈希/凭据版本/epoch，复用 `verify_password`；昂贵计算避免阻塞事件循环。
4. 外部网络调用不在注销事务内，注销本身也不需要调用 OJ。

### 10.2 同一独立连接的短写事务

```text
BEGIN IMMEDIATE
  复查已提交幂等结果
  重读 actor/target、生命周期、角色、凭据版本、密码哈希和 account_epoch
  确认锁外密码验证对应的哈希/版本仍然有效，否则拒绝
  复查策略、明确确认、角色交接和所有阻断项
  标记 users.closed，增加 account_epoch；所有登录凭据撤销
  清空全部 OJ 绑定，确保五个平台绑定版本均比事务前大
  按第 8 节删除本人私有数据，处理通知与公共作者展示所需状态
  将该成员任务标为取消并清理任务快照中的个人资料
  撤销待删资源的 URL 可访问性，写入资源清理发件箱
  插入唯一注销结果与成功审计
COMMIT
```

提交后才清当前会话、返回成功并唤醒清理工作器。`BaseException/取消/数据库异常` 均保证回滚或查明提交结果；提交响应丢失由回执确认，不能靠前端猜测。

所有状态/版本/数据清理必须共用同一事务连接，不调用会自行 commit 的普通绑定/同步 API。可复用其事务内底层函数，必要时拆出无自动提交的 helper。

### 10.3 绑定触发器的特殊处理

当前清空非空 OJ 字段会触发现有数据库版本递增与记录清理；原本为空的字段不一定触发。实现要记录事务前版本，在清空后确保所有版本均至少为“旧版本 + 1”，不要归零，也不要假定触发器一定只加一次。复用现有归一化平台名和别名规则。

不得持有 SQLite 写锁等待网络、文件大批量 I/O、发送消息或执行耗时密码计算。大数据量账号应在测试副本测量耗时；若单事务规模不可接受，需单独评审 `closing` 状态和分批清理，不能悄悄改成非原子删除后仍报完整成功。

## 11. 多入口防恢复与并发边界

### 11.1 共用守卫，而不只封新路由

| 入口 | 必须补的检查 |
| --- | --- |
| 登录、`_session_identity`、改密 | 联查 lifecycle，closed 一律拒绝；登录使用通用失败信息，避免泄漏谁已注销 |
| 单个开户、批量发密码、账号启用、角色变更、两种密码重置 | 在写事务中拒绝 closed；不允许普通“启用”变成恢复 |
| 成员资料修改、改头像、OJ 验证/确认/解绑 | 权限和生命周期在最终写事务内重检，不能只靠请求前置装饰器 |
| 帖子/评论/通知/工作台/训练生成 | 最终写入前验证 actor/owner 仍 active，避免请求在注销前进入、注销后完成写入 |
| QQBot `PUT users`、资料更新、自动建档、绑定验证/确认 | 共用生命周期服务；closed 返回结构化失败，不重建、不补全资料 |
| QQBot `DELETE users` | closed 墓碑禁止删除；已有 Web 账号不能再走物理删除来替代本人注销；无 Web 账号的旧行为另行核对，不绕过角色/公共引用保护 |
| 自动同步扫描、重试与手动同步排队 | 排除 closed；排队载荷带 epoch，不只带 QQ |
| 初始 root bootstrap | 不能因为账号被注销/停用就重跑开户；命中 closed 主体明确拒绝并交运维处理 |
| #84 Excel 导入 | 预检和执行都返回 ACCOUNT_CLOSED/REOPEN_UNSUPPORTED；不能只预检一次，提交时仍需复核 |
| Android 当前/待合入接口 | 所有鉴权复用同一身份解析；客户端清缓存不是服务端的唯一防线 |

建议增加数据库层窄约束，防止 closed 生命周期被普通 UPDATE 改回 active、closed 墓碑被物理删除。禁止在这些路径使用 `INSERT OR REPLACE users`。约束实现必须测试迁移、UPSERT 和触发器行为；它不能替代应用层权限或完整 owner 检查。

### 11.2 旧同步任务不能回写

- 队列项/任务快照记录 `{qq_id, account_epoch, platform, binding_version, binding_key}`。
- `BindingGuard`、CF 每页历史写入、同步状态更新、最后同步时间更新、任务分项结果更新，都在实际写事务内验证：生命周期 active、epoch 相等、绑定版本/账号相等。
- 快照没有 epoch 的旧任务在启用注销功能前应停止/标记中断重新排队，不把缺失字段当成“跳过检查”。
- 不依赖 `asyncio.Task.cancel()`：上游请求可能已经返回，取消不保证数据库不会提交。取消只是节省工作，最终守卫才是正确性边界。
- 若旧任务先提交，注销事务会清掉它刚写的数据；若注销先提交，旧任务拿到写锁后复核失败并回滚。两种顺序都不留下恢复数据。
- 给同批其他成员保留执行机会；全局题库元数据可以继续更新，但任何成员资料、结果快照不得回填 closed 用户。
- 通知外发在发送前再次检查；已经发送给外部系统的消息无法保证撤回，必须在影响说明中承认边界。

## 12. 资源文件、缓存与不可变历史

### 12.1 先撤销访问，再异步删除

数据库状态关闭不等于旧资源 URL 消失。尤其当前头像路由直接按文件名提供文件，应补充“仍被有效主体引用/未撤销”的判断；发件箱待删项可作为撤销登记，或新增等效受控资源索引。

- 清理事务内保存安全的存储标识并撤销访问，不能把原始 URL 当文件路径。
- 头像旧 URL 立即返回 404；条件请求不得返回旧 304/重定向或旧缓存正文。响应缓存策略和反向代理缓存一并验证。
- 社区图片和 Markdown 资源按现有引用/访问控制处理；已发布内容仍引用的资源继续可读，其 owner 展示和编辑权限去标识化。
- 只删除已经确认无保留引用的资源；使用现有引用检查，事务内再核验，不按 owner 整批删文件。
- 工作器校验解析后的绝对路径在配置的受控资源目录内，不跟随越界链接，不接受客户端路径；只操作列明资源，缺失即幂等完成。
- 失败保存错误码并告警，可恢复清理；不把物理文件失败回滚为账号可登录。

浏览器或第三方此前保存的公开资源副本无法可靠收回，不做技术上无法保证的承诺。

### 12.2 缓存、搜索和快照

排查成员/排行榜缓存、帖子作者缓存、通知缓存、Wiki 派生展示、搜索索引、CF job JSON 和服务进程内用户快照。每个含身份的缓存须有失效或投影过滤；不能只改 SQL 字段而继续从旧内存对象返回姓名/头像。

最新 main 已合入 Wiki 公开响应缓存。缓存键依赖 `wiki_settings.public_content_version`；注销改变作者派生展示时，在同一注销事务内增加该版本，所有进程的新请求就会使用新键。需要的本进程缓存清理只是优化，不能代替数据库版本失效，也不能只等当前 300 秒 TTL。补充“先预热缓存 → 注销 → 携旧 ETag 重读”的测试，确保变化后的正文不会被旧 304 或旧响应恢复；保持版本读取和数据读取的 WAL 快照一致性。

当前 Wiki 修订不可变，**不要关闭不可变触发器来匿名化作者**。将关闭状态用于派生展示，并限制原始 author 的读取与导出；全文中的本人信息按已确认的内容处理政策人工处置。

## 13. 前端交互与现有请求封装衔接

### 13.1 用户流程

1. 在 `Home.vue` 的账号安全区域增加低干扰的“注销账号”入口，不挤占正常退出登录按钮。
2. 进入独立确认视图，展示处理清单、保留范围、不可恢复提示与职责交接阻断项。
3. 输入当前密码，勾选阅读影响，输入固定确认文字“注销账号”。确认前不自动触发任何解绑/删除。
4. 提交后禁用重复点击，保持可访问性焦点和加载状态；不因前端超时立刻宣布失败或成功。
5. 成功后清本端认证、个人列表、头像预览、通知、管理缓存与轮询，转入最小结果页。
6. 结果页显示账号关闭与资源清理状态；网络不确定时只查最小回执，不重复创建新操作。

建议新增 `views/AccountClosure.vue`；实际路由可为 `/account-closure.html`，由现有 router 管理。错误返回个人中心、浏览器后退、刷新与首次改密回跳都要测试。

### 13.2 必须处理现有封装的 401 自动跳转

当前 `lib/api.js` 对非 auth 接口的 401 会直接跳登录页，并使用 session version 丢弃旧响应。注销结果确认需要一个局部、受控的“不自动跳登录，仅返回错误”模式或专用回执请求函数：

- 只用于注销提交/最小回执，不削弱其他接口默认行为。
- 确认提交或确定会话失效后调用统一认证清空，防止旧请求覆盖结果状态。
- 记录操作 ID/回执秘密后再清普通用户状态；不要把本次回执随通用 logout 一起清掉导致超时无法恢复。
- 多标签可用 `BroadcastChannel` 发送不含秘密的 session-invalidated 事件；其他页清缓存，服务端仍负责最终拒绝旧会话。
- 结果页不得把普通 `auth/me` 返回未登录误当成“本次注销成功”。

### 13.3 管理页最小配合

`Accounts.vue` 仅增加“已注销”状态和操作禁用原因；账号启用、重置密码、发放临时密码、改角色按钮对 closed 不可用。成员身份、登录停用和注销分开显示，后端也同样拒绝。公共列表、导航和弹窗改造仍交 #85，避免重复实现。

## 17. 数据库迁移、发布与回退

### 17.1 迁移原则

1. 先部署兼容守卫版本，新增字段默认为 active、epoch=1；不按停用或成员 status 猜测历史注销。
2. 新增表和索引使用幂等迁移；记录迁移版本、校验备份与外键约束。
3. 数据初始化/迁移不创建测试账号，不执行生产清理，不自动修改现有角色。
4. 用脱敏旧库副本测试大账号、历史外键、Wiki 触发器和资源引用；记录耗时与失败处理。
5. 先停止/排空旧同步和写入进程，所有节点/服务更新并确认后，才开启注销能力。缺少 epoch 的旧任务不能继续执行。

### 17.2 发布门槛

- P01–P08 已确认，隐私告知与实际实现一致；跨人评审和所有适用测试通过。
- QQBot 与 Android 当前部署版本已完成联调；如果某端仍可绕过，功能保持关闭，不宣称整站注销完成。
- 取得数据库、头像、社区图片、Markdown 资源的一致备份；运维确认恢复步骤，不能在 WAL 运行中只复制单个 `.db` 文件充当完整备份。
- 记录源码/前端制品版本、配置键、迁移版本、发布人、观察指标、回退限制。
- 本仓库 `feat/**` 合 main 会自动同步，因此上述检查必须在合并前完成。提交者不自行合并。

### 17.3 回退不能恢复账号

- 出现故障先关闭“接受新注销”的入口并暂停相关写入/清理工作器，保留既有 closed 检查和凭据撤销。
- 注销数据清理不可逆；撤销代码不等于恢复资料，禁止把旧备份直接覆盖线上后开放登录。
- 任何回退版本必须认识 closed/epoch；否则进入维护状态，不能运行不认识注销状态的旧写入服务。
- 若必须恢复备份，先保存最新墓碑、注销审计、凭据版本与资源撤销清单，恢复后重放关闭和清理规则，再恢复流量。
- 如无法证明最新注销清单完整，保持登录/同步关闭，交运维恢复 WAL/审计并核验；不得以“服务先起来”为由重新激活账号。
- 灾难恢复时还需使旧 Cookie 全部失效并确保 OJ 绑定版本不倒退；这是恢复专用措施，不是每次本人注销都踢掉全站会话。
