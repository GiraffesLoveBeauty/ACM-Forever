# Web 双入口加载实测：2026-11-03

这是当前生产入口的诊断基线，关联 Issue #54、#74。没有网络调整前的历史采样，也没有核实生产部署提交，因此不据此关闭历史验收任务或认定某一网络组件是根因。

本记录采自工具最初版本。当时的成功标准为导航与目标 DOM 可见；后续 review 修订增加了业务响应校验及场景发现结果归档。下方历史数字保持原始口径，没有重新采样或补造这些字段。之后对照应使用修订后的工具，并核对每个入口的 `discovery` 覆盖范围与 `business` 错误。

## 阶段与资源证据

两个入口冷访问文档的 15 个样本中，TLS 中位数分别约 0.436 秒、3.325 秒，文档 TTFB 分别约 0.512 秒、0.998 秒。文档阶段已经存在差异，但 B 的首次内容还要更久，需继续看后续静态资源。

以下是各入口 15 次冷访问中相同资源的中位数。`bodyBytes` 是传输时编码后的正文大小，表中不含响应头；总耗时包含连接、等待和下载，不是服务器 CPU 时间。浏览器并行下载，不能将各行相加当作页面耗时。

| --- | --- | --- | --- | --- |
| `index-LUTpu1wS.js` | 55.4 | 135.3 | 833 | 7,932 |
| `katex.min.js` | 78.7 | 266.5 | 808 | 9,983 |

A 首页 `/assets/` 冷访问总传输中位数约 282 KiB，B 约 932 KiB；两者热访问该合计均为 0，符合浏览器静态缓存命中的现象。B 的上述 CSS 下载阶段中位数约 6.84 秒，KaTeX 脚本约 6.05 秒，主脚本约 5.33 秒。A 主脚本的补充 HEAD 请求返回 `Content-Encoding: br`；B 的补充浏览器 GET 返回 200、`Content-Length: 138565`、`Cache-Control: public, max-age=43200`，没有 `Content-Encoding`。这支持优先核查 B 的静态压缩与代理配置；仍需按同一工具复测，不能仅凭这些时间归因 Tailscale 隧道或服务器带宽。

排行榜还需单独检查图片。A 的默认头像资源编码正文约 1.11 MiB，比首页核心静态传输合计更大；B 有 2 次默认头像请求未完成。图片体积、缓存与失败重试值得优先排查，但本次没有修改这些资源。

每次首页观察到 4 个同源 API 请求，Wiki 入口 3 个、排行榜 2 个、帖子 2 个、Wiki 文章 3 个。Wiki 导航响应已有 `Server-Timing`：可观察到缓存命中，查询与 JSON 阶段为 0、版本检查约数毫秒。浏览器中仍然存在数百毫秒至秒级等待，不能把整段 TTFB 直接解释成数据库查询慢。

## 失败记录与限制

- 60 次导航与目标 DOM 匹配均成功，没有因导航或 DOM 等待失败而丢弃的页面耗时；成功口径以页首版本说明为准。
- A 每次访问都有一个外部 `beacon.min.js` 请求失败，共 30 次。它与目标正文成功同时存在，不能记成 30 次业务页面失败。
- B 共 2 次 `/assets/default-avatar.png` 请求失败；其余已记录资源错误为 0。未完成资源不会产生完整 Resource Timing，传输合计可能偏低。
- A 的 12 次独立 HTTP 探测均成功。`/health` 总耗时中位数 1,679 ms；分类 453 ms；帖子列表 447 ms；Wiki 导航 643 ms。Wiki 导航探测均返回缓存命中信息。
- B 的独立探测只有第 1 次 `/health` 成功（114 ms），其他 11 次均在 30 秒超时；浏览器对应 API 与目标页面却能完成。独立请求栈和浏览器请求栈的访问表现不同，故不能把这些超时计为浏览器 API 耗时或断言网站不可访问。工具因保留这些失败返回非零退出码。
- 没有服务器日志、带宽监控、历史调整前数据或确认的部署提交，不能据此给出链路根因或发布前后提升比例。

## 后续验收

优先检查 B 静态响应的压缩和传输，再缩小排行榜默认头像并核对缓存；同时在服务器日志里对应慢请求与 Wiki 的 Server-Timing。核实生产提交后，在同设备、网络和场景下，避开本地回归负载重新采样。网络调整的前后对照仍需真实历史基线或之后受控的运维实验。
