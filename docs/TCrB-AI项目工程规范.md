# AI 项目工程协作规范（讨论稿）

> **状态：讨论稿，待小组确认。** 本文同步自 CJLUACM-DLC 已合入的规范，结合 ACM-Forever 的仓库定位与现有工作流补充说明。新增规范建议不代表已经通过的小组决议，也不代表相关检查或部署机制已经配置。

同步来源：[TCrB-AI项目工程规范.md（CJLUACM-DLC 原文，版本 3ec10d9）](https://github.com/GiraffesLoveBeauty/CJLUACM-DLC/blob/3ec10d9a05b42be05245f6fd2c8e55bbe0bae814/docs/TCrB-AI项目工程规范.md)。跨仓库引用固定到该版本，便于核对后续修订。

适用于参与多人、多组软件项目开发的 AI 代理。AI 负责辅助实现、验证、文档整理和技术细节审查；需求目标与方案共识由项目成员确认，PR 由另一位成员评审，发布与故障恢复由运维负责人组织。

CJLUACM-DLC 是前期讨论与方案文档仓库，其文档维护与 Git 操作遵循该仓库的 [AGENTS.md（AI 协作规则）](https://github.com/GiraffesLoveBeauty/CJLUACM-DLC/blob/3ec10d9a05b42be05245f6fd2c8e55bbe0bae814/AGENTS.md)。ACM-Forever 是工程代码仓库，目录与部署说明见 [README.md（项目说明）](../README.md)，安装、启动与测试说明见 [feat/api/README.md（独立 API 服务）](../feat/api/README.md)。纯文档改动按其实际影响进行检查。

原会议中的发布方式尚未确定，见 [03-协作与发布.md（开发与发布讨论）](https://github.com/GiraffesLoveBeauty/CJLUACM-DLC/blob/3ec10d9a05b42be05245f6fd2c8e55bbe0bae814/docs/meeting-202610021400/03-协作与发布.md)。ACM-Forever 当前的 [sync-feat-to-server.yml（服务器同步工作流）](../.github/workflows/sync-feat-to-server.yml) 在 `feat/**` 或该工作流文件变更推送到 `main` 时触发，也支持手动触发。因此，涉及这些路径的改动应按合并即发布处理，联调验收和运维发布确认必须在合并前完成。仅修改 README 与本规范不触发当前自动部署；实际部署状态仍需运行验证。

## 1. 开始任务前

- 阅读仓库说明、适用的 AI 协作规则及相关需求文档，区分讨论稿、待确认方案、已确认结论和实际实现。工程任务还应阅读安装、启动、测试和代码规范，确认依赖版本与检查命令；发现说明缺失时补充文档。
- 确认任务所属模块的职责、接口、依赖和维护者。跨组改动先约定接口及联调方式，不随意改动其他模块的内部数据。
- 按 [02-架构与数据.md（后端解耦与数据边界）](https://github.com/GiraffesLoveBeauty/CJLUACM-DLC/blob/3ec10d9a05b42be05245f6fd2c8e55bbe0bae814/docs/meeting-202610021400/02-架构与数据.md) 中的方向，Web、后续移动端和机器人通过统一后端 API 使用数据，数据库访问集中在平台后端。实现前核实现有接口、表结构与数据来源，不把文档中的示例当作已存在的能力。
- 将需求拆成可验证的小改动，尽早集成并检查完整流程。Git 无文本冲突不等于行为兼容。

## 2. 分支与改动范围

- 修改前确认分支和工作区状态，保留与当前任务无关的文档和改动。从共同主分支建立短期任务分支，合并后删除；不长期保留小组独立分支。
- 建议分支名使用 `<类型>/<负责人ID>-<任务简述>`。负责人 ID 在团队内保持唯一，用于区分不同人的工作；任务简述应指向具体事项。该格式是规范建议，具体命名按工程仓库确认的约定执行。
- 根据改动的主要目的选择以下四种类型：

| 前缀 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变外部行为的代码结构调整 |
| `docs` | 文档修改 |

例如：`feat/zc-nowcoder-crawler`。一个 PR 只解决一个连贯问题。

## 3. 实现、测试与文档

- 遵循仓库的格式和检查规则；提交与任务相关的源码、测试、文档及构建配置。提交前检查差异，只暂存本次相关文件。
- 为核心业务、公共接口和缺陷修复提供相应单元测试；跨模块流程补充联调验证，并记录实际验证结果。
- 接口、配置或使用方式变化时，同步更新仓库内的 Markdown 文档。文档改动建议用独立的一个或多个 commit 提交，与主要功能代码的 commit 分开；相关文档仍可放在同一个 PR 中。
- 工程规范与接口说明放在 `docs/`，前期讨论、需求与会议材料保留在 CJLUACM-DLC。新增或移动项目文档时，更新根目录 README 的文档入口，链接文字采用“文件名（简要标题）”。保留作者原意，注明文档状态。
- 纯文档修改检查 Markdown 格式、相对链接和图片路径，提交前运行 `git diff --cached --check`。当前 [api-tests.yml（API 自动检查）](../.github/workflows/api-tests.yml) 按路径触发，覆盖 `docs/api.md`、`feat/api/**` 和该工作流文件；仅修改 README 与本规范时需完成本地文档检查，不把未运行的自动检查写成通过。
- 不提交密码、真实配置、缓存或生产数据；开发与演示使用测试数据或脱敏样例，不向外部 AI 工具提交未经授权的真实学生信息或数据库凭据。

## 4. PR 与评审

- PR 描述写清要解决什么、为什么做、主要改动、涉及的接口、验证结果和已知风险；纯文档 PR 可简要说明文档内容与检查结果。
- 提交者主动邀请另一位成员评审，并向其解释功能目标与核心思路。评审者先确认需求理解和方案方向，再借助 AI 检查代码实现、接口和字段定义等细节。跨模块改动还需与相关负责人对齐。
- `main` 只通过 PR 合并；自动检查和跨人评审通过后，由非提交者且有权限的成员合并。提交者不自行点击合并；禁止直接推送或强制推送 `main`，包括 `--force` 和 `--force-with-lease`。
- 工程仓库建议将必要自动检查配置为 `main` 合并的必需检查；合并与生产部署使用已通过检查的版本，有新提交时重新检查相应版本。不能把此建议写成当前已启用的分支保护。
- 若合并会直接触发生产部署，联调验收与运维发布确认也必须在合并前完成；若发布单独触发，则在生产发布前完成相应确认。
- 实际提交、推送和合并按用户要求执行；修订或撤销已合入的内容，也通过新 PR 完成。

## 5. 联调验收与生产发布

本节适用于工程仓库中涉及业务功能或部署的改动；纯文档改动按文档检查与 PR 流程执行。

- 合并前在任务分支对应的本地或独立测试环境进行与改动相关的联调和验收，确认完整流程可用，并记录验收结果。
- 生产发布前向运维负责人提供待发布的源码与制品版本、变更说明、配置及数据库变更信息，由其确认发布条件；提前明确生产观察指标和恢复步骤。
- 涉及数据库变更时，发布前核验新旧版本兼容性、准备可恢复备份，并约定迁移和恢复步骤；不能假设撤销代码就能恢复数据库。若合并即发布，上述准备应在合并前完成。
- 按工程仓库确认的方式触发部署。手动触发、通过 `deploy` 分支触发或合并 `main` 自动部署，都需在采用前写清触发条件和发布责任；本规范不代替团队完成选型。
- 发布后进行生产验证，检查部署结果、服务健康、关键业务流程和数据状态；发现异常时，由运维负责人组织按预定恢复步骤处置，AI 配合排障。

## 执行顺序

**纯文档改动：** 明确文档目的与状态 → 建立任务分支 → 文档更新与 README 入口维护 → 检查格式和相对链接 → 提交 PR → 跨人评审与适用的自动检查 → 非提交者合并 `main`。

**工程仓库：** 明确需求 → 约定接口 → 建立任务分支 → 开发、测试与文档更新 → 提交 PR 并说明目标 → 跨人评审、自动检查与联调验收 → 非提交者合并 `main` → 运维确认发布条件 → 按约定触发生产部署 → 生产验证。

若合并 `main` 会触发生产部署，则将“运维确认发布条件”提前至合并之前；当前 ACM-Forever 涉及服务器同步触发路径的改动按此执行。
