# App 专用 API 实施方案

状态：2026-10-14 已获准在先同步最新代码后修改本地后端。本地已实现下列接口并接入客户端，远端更新与生产部署等待单独审批；验证结果见 [更新申请.md](更新申请.md)。基线提交为远端 main 的 `cbf700c`。

## 连接结构

```text
安卓 App → 手机可访问的 HTTPS 服务 → /api/mobile/v1/* → 现有业务逻辑 → 现有 SQLite 数据库
```

后端统一管理数据库连接、权限、统计和写操作。App 通过 API 使用数据库中的数据；数据库文件与服务端密钥留在服务器。新增 API 使用现有服务监听端口，不需要为每个接口另开 TCP 端口。

Tailscale 解决设备到内网主机的连通性。新增业务接口不能自动将内网服务变为公网服务；若只通过 Tailscale 发布，电脑与手机均需加入有访问权限的内网。若提供正式 HTTPS 对外入口，手机可经该入口调用。具体域名、访问范围和运维配置需由服务器负责人确定。

## 首批接口

现有登录、退出、改密、本人题库、发帖、昵称与头像接口继续使用；新增接口专门提供 App 所需的公开资料与稳定身份关联。

| 方法与新路径 | 用途与返回内容 | 权限 |
| --- | --- | --- |
| `GET /api/mobile/v1/capabilities` | 协议版本与可用功能标识，让 App 判断已开通能力 | 公开 |
| `GET /api/mobile/v1/leaderboard` | 沿用现有公开排名口径与分页，补充 public_member_id | 公开 |
| `GET /api/mobile/v1/forum/posts` | 现有公开话题列表，补充作者的 public_member_id | 公开 |
| `GET /api/mobile/v1/forum/posts/<id>` | 现有已发布话题及评论，补充公开作者关联 | 公开 |
| `GET /api/mobile/v1/members/<public_member_id>` | 用户名、头像、身份、座右铭、各平台生涯通过题数与合计 | 公开 |
| `GET /api/mobile/v1/members/<public_member_id>/posts` | 仅该成员的已发布话题，分页 | 公开 |
| `GET /api/mobile/v1/me/public-profile` | 会话本人对应的公开资料，准确定位底部个人中心 | 登录成员 |
| `PUT /api/mobile/v1/me/public-profile` | 仅修改本人的座右铭，长度及类型校验 | 登录成员 + CSRF |

查询参数、分页上限、平台键与统计口径复用现有接口。公开接口不返回 QQ 号、真实姓名、学校、绑定标识、逐题记录、收藏、草稿和审核中帖子。公开 ID 使用不含个人信息的随机稳定标识，不根据昵称或头像猜测关联。

登录首版复用现有 `/api/auth/login`、`/api/auth/me`、`/api/auth/logout` 的 Cookie 会话与 CSRF 校验。是否增加长期登录、刷新凭据和设备会话管理另行约定；首批公开接口不要求修改已确定的登录策略。

## 数据与兼容

- 在后端新增公开资料映射存储：关联现有成员、唯一 public_member_id、座右铭与更新时间；随机 ID 一次生成后保持稳定，避免公开 QQ。
- 通过数据库已有的幂等初始化/迁移方式创建新表和索引，不替换数据库，不改现有字段含义。既有成员分配 ID 的方式在实现前核对现有数据库初始化流程。
- 原 Web API 路径及响应保持兼容，既有网页继续调用原接口。App 专用 API 复用业务查询与权限校验，避免重复计算或让手机直接访问数据库。
- 缺失能力在对应区域显示红色“无API接口”；断网、超时与服务器错误分别显示。不提供接口记录菜单或演示数据。

## 验证顺序

1. 临时数据库与合成成员验证：匿名公开读取、本人编辑、跨成员不可写、CSRF、分页、ID 稳定、既有数据兼容和原 Web 契约。
2. 加入 Tailscale 内网，核实服务器当前服务监听与部署版本，确认手机最终使用的 HTTPS 入口。
3. 部署获准版本后验证公开 API 和测试账号的只读本人接口，再验证 Android 真机访问。涉及生产写入的验收使用指定测试账号与明确的测试数据。
4. 验证对应真实数据或错误状态并生成新版 APK；安装和应用内 APK 更新仍需真机验证。
